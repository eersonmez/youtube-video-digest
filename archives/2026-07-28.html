Introducing gpt-transcribe and gpt-live-transcribe

OpenAI introduces gpt-transcribe and gpt-live-transcribe as two transcription options. gpt-transcribe processes a completed audio file and returns a full transcript, while gpt-live-transcribe maintains an open connection and produces text as audio arrives. Both support 57 languages and are designed to improve difficult cases involving accents, multilingual speech, very short answers, names, and numbers. Developers can provide prompts and specialized vocabulary, including proper nouns and code terms, to improve recognition of important words. The models are also intended to reduce background noise, side conversations, and ambient music being mistaken for speech. Live transcription can follow language changes within one session, including switching between English and Spanish. A roughly 30-minute meeting recording was processed in just under a minute, illustrating gpt-transcribe's fit for archives, podcasts, and batch jobs, while the streaming model targets captions, dictation, and voice interfaces where latency matters.

  • gpt-transcribe converts completed audio files into full transcripts.
  • gpt-live-transcribe returns text continuously over a live connection.
  • Both models support 57 languages and improved handling of accents, names, numbers, and multilingual speech.
  • Developers can provide prompts and specialized vocabulary for important terms.
  • Noise handling helps exclude side conversations and ambient music.
  • gpt-transcribe suits batch jobs, while gpt-live-transcribe targets low-latency interfaces.

A security talk on prompt injections, indirect attacks, and backdoors affecting LLM applications and model files.

NDC Conferences · 2026-07-28T13:00:10+00:00

Doors of (AI)pportunity: The Front and Backdoors of LLMs - Kasimir Schulz & Kenneth Yeung

Kasimir Schulz and Kenneth Yeung of Hidden Layer explain LLM "front doors," especially prompt injection, alongside conventional and model-level "backdoors." They describe LLMs as token-prediction systems whose generated sequence can create a "freight train effect," while system prompts guide behavior but do not provide complete protection. Demonstrations cover bypassing content restrictions through concept decomposition and image-to-text prompting, universal and transferable jailbreaks that target instruction hierarchy, and an indirect prompt injection hidden in an email retrieved by Gemini for Workspace's RAG system. The talk then examines model-loading risks: formats using Python pickle, trust remote code, and repository sideloading, contrasting them with safer safetensors and ONNX limitations. Using Netron, they show a computational-graph backdoor triggered by a red image feature and a conditional modification that restores a refusal-bypassing vector. The closing takeaway is to use multiple defensive layers and treat indirect inputs as untrusted.

  • Prompt injection can steer an LLM toward attacker-chosen output and create a freight-train continuation effect.
  • System prompts establish context and instruction priority, but simple protections are not sufficient.
  • Indirect prompt injection can hide in retrieved email content and target Gemini for Workspace users.
  • Model-loading risks include Python pickle, trust remote code, and repository sideloading.
  • Computational-graph backdoors can activate on a visual trigger while preserving normal outputs.
  • Multiple defensive layers are needed for LLM applications and their inputs.

The talk explains how behavioral economics can improve secure software development by addressing developer behaviors that produce insecure code.

NDC Conferences · 2026-07-28T12:00:03+00:00

Threat Modeling Developer Behaviour: The Psychology of Bad Code - Tanya Janca

Tanya Janca argues that insecure software is often a behavioral and cultural problem, not simply a lack of knowledge. Drawing on behavioral economics, she proposes interventions that make secure choices easier without manipulating developers: secure defaults, reusable known-good templates, security activities throughout the SDLC, IDE and pre-commit tooling, social learning, reminders, and recognition. She identifies recurring patterns such as vibe coding with insufficient AI-code review, rushing under deadlines, copying online examples without context, neglecting documentation, satisficing error handling, skipping tests, overengineering for status, and superficial or absent code reviews. The associated biases include automation bias, present bias, authority and availability heuristics, effort discounting, the tragedy of the commons, diffusion of responsibility, and moral licensing. Janca recommends measuring changed behavior, making maintenance work visible, gating merges on passing tests, rewarding simplicity, and building accountability carefully through reviews and postmortems.

  • Treat insecure coding as a behavioral and cultural issue, not only a training gap.
  • Use secure defaults, known-good templates, and security checks at every SDLC phase.
  • AI-assisted vibe coding and superficial reviews can create automation bias and diffusion of responsibility.
  • Make documentation, testing, simplicity, and secure fixes visible and rewarded.
  • Measure whether behavior changes rather than merely tracking training completion.

AI red teaming techniques for finding and mitigating vulnerabilities in AI agents and language-model applications.

NDC Conferences · 2026-07-28T11:30:27+00:00

How to Break AI Systems (Before Someone Else Does) - Gary Lopez - NDC Toronto 2026

Gary Lopez’s NDC Toronto talk explains AI red teaming as adversarial and collaborative testing of AI systems for reliability, bias, privacy, harmful content, deception, psychosocial harm, agentic behavior, and dangerous knowledge-to-action capabilities. He illustrates consequences with Google Bard’s incorrect James Webb Space Telescope claim, a chatbot’s misleading airfare-refund guidance that led to legal liability, and other hallucination and misuse examples. The central technical problem is that language models combine system prompts, user input, and external data without a strong data-code separation, making jailbreaks and direct or indirect prompt injection possible. Lopez describes attacks using encoded text, gradual “Crescendo” conversations, and malicious instructions hidden in webpages, email, or documents. He recommends mitigations including spotlighting through delimiters, data marking, or Base64 encoding, plus input and output classifiers, harmful-content and prompt-injection detection, personally identifiable information checks, and fact checking.

  • AI red teaming covers reliability, bias, privacy, harmful content, deception, and agentic risks.
  • A weak separation between data and instructions enables jailbreaks and prompt injection.
  • Direct attacks manipulate user input, while indirect attacks hide instructions in webpages, email, or documents.
  • The Crescendo technique gradually shifts a benign conversation toward harmful requests.
  • Spotlighting uses delimiters, data marking, or encoding to help models distinguish data from instructions.
  • Input and output guards can detect harmful content, jailbreaks, personal information, and unsupported claims.
