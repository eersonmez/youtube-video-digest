A security talk on prompt injections, indirect attacks, and backdoors affecting LLM applications and model files.

NDC Conferences · 2026-07-28T13:00:10+00:00 · Doors of (AI)pportunity: The Front and Backdoors of LLMs - Kasimir Schulz & Kenneth Yeung

What This Video Is About

In this security talk, Kasimir Schulz and Kenneth Yeung of Hidden Layer use “front door” to describe prompt injection and “backdoor” to describe malicious behavior hidden in software or machine-learning models. The talk begins with how large language models generate text: they predict one token at a time and append each prediction to the growing sequence. That process can create a “freight train effect,” where a model that has started moving toward an attacker’s desired continuation keeps generating in that direction rather than stopping to correct itself.

The speakers then demonstrate several ways to bypass simple safeguards. These include direct prompt injection, concept decomposition using the model’s implicit knowledge, multimodal prompt attacks, automated jailbreak discovery, and a technique they call Policy Puppetry that targets the model’s instruction hierarchy. They emphasize that system prompts are useful for guiding a model but are not a complete security boundary.

The second half shifts to indirect prompt injection and model supply-chain risk. Retrieved emails, web pages, reviews, calendar invitations, and code repositories can carry hidden instructions that an LLM processes as context. Separately, model files may contain executable Python, redirect a loader to unreviewed code, or embed malicious logic in a computational graph. The closing recommendation is defense in depth: treat indirect inputs as untrusted, carefully inspect model-loading paths, and do not rely on a single system prompt or file extension. The healthcare example in the talk is an illustration of a safety bypass; it is educational and not personal medical advice.

Detailed Walkthrough

Prompt injection as an LLM “front door” [0:00]

The talk opens with a demonstration in which one speaker asks ChatGPT to explain prompt injection. The response falsely claims that prompt injections are safe and unimportant. The explanation is that a large block of text was inserted into the conversation context while the other speaker was occupied. That inserted text instructed the model to produce the desired answer instead of the truthful one.

The speakers compare this with SQL injection. In a conventional SQL injection, a trusted query is combined with untrusted user input. If the input is malformed or malicious, the final query can perform unintended actions. Prompt injection follows the same broad pattern: a trusted system or developer prompt is combined with untrusted user text, retrieved documents, tool results, or other inputs, and the combined context is given to the language model.

To explain why this works, the speakers reduce an LLM to its basic generation loop. The model does not operate by writing a complete answer and then revising it in the human sense. It predicts one more token. If the context is “roses are red, violets are,” the expected next token might be “blue.” That token is appended to the context, producing “roses are red, violets are blue,” and the model predicts the next token again. The same mechanism produces longer email drafts, stories, and agent responses.

The “freight train effect” describes what happens when an early prediction points toward an attacker’s preferred sequence. Because each generated token becomes part of the next input, the model has momentum in that direction. The speakers stress that a model cannot simply look back at a previously generated token and correct the entire sequence in the way a person might reconsider a sentence.

System prompts help, but do not fully protect an application [5:00]

The first direct attack demonstration uses a SQL agent with several attached tables. Its system prompt describes the agent and explicitly says never to use a `DROP TABLE` query. A simple attack that says to ignore the previous instructions and run `DROP TABLE employee` is blocked.

This illustrates the legitimate role of a system prompt. It provides context, describes what the model is allowed to do, establishes restrictions, and can tell the model which tools are available. In the SQL example, the explicit prohibition significantly reduces the probability that the model will produce the dangerous query.

The speakers immediately qualify this result. A system prompt can stop a straightforward request, but it does not enumerate every way that a model could construct an equivalent result. Blocking every possible wording or combination would be impractical. The model can sometimes assemble a forbidden sequence indirectly from concepts that are individually allowed.

CROP and knowledge-based concept decomposition [5:00–15:00]

The talk introduces a technique called CROP, expanded in the transcript as “knowledge return oriented prompting.” The general idea is to use knowledge already present in the model rather than directly writing the prohibited phrase or request.

The first example uses XKCD 327, the “Little Bobby Tables” comic about SQL injection. The model has likely encountered the comic during training. Instead of asking the model directly to produce `DROP TABLE employee`, the attack refers to the known story and instructs the model to manipulate pieces of it: remove text before and after a semicolon and replace the name of a student table with the target employee table. The resulting sequence contains the dangerous query even though the literal phrase was not directly included in the prompt.

This defeats a narrow system-prompt rule because the rule only said not to use a particular query. It did not prevent the model from transforming a known reference into that query. The speakers present this as analogous to using a “gadget” in exploit development: an attacker finds an existing sequence or fact and combines it with other instructions to obtain a desired effect.

The same concept is demonstrated with image generation. A request involving Pikachu drinking beer at a juice shop is rejected by the image model. The speakers decompose the request into cultural references and related concepts that the model may know separately. They then combine those references into a new prompt and claim that the image generator produces the previously blocked result.

The next example reverses the modality. Instead of using text to generate an image, the speakers use an image to help generate text. The image depicts a “reverse” sign and a shell, while accompanying text tells the model to combine the concepts. The model produces a Python reverse shell and explains how it combined the image concepts. The speakers say that a few additional prompting lines could remove the explanation and return only the code, which would make the technique more useful in an automated or agentic workflow. This is presented as a security demonstration, not as a recommendation to create malware.

The speakers also discuss their internal tool, AutoCROP. They compare it with tools that search for return-oriented-programming gadgets. Instead of requiring a researcher to manually identify a useful cultural or textual reference, AutoCROP uses a language-model chain to test candidate transformations iteratively. It attempts to find a working gadget for a target string when such a gadget exists. The talk mentions `sudo rm -rf` as one example of a target string used while exploring the technique, but the excerpt does not provide the result of that test.

Universal, transferable jailbreaks and instruction hierarchy [15:00]

The speakers define three properties of some of these attacks:

  • “Universal” means the same attack works against multiple language models trained on similar data.
  • “Transferable” means the same exploit can be sent unchanged to different users, even if they use different models.
  • “Alignment bypass” means the attack circumvents safeguards added by model providers or application developers.

They say they have demonstrated related attacks against Claude, several ChatGPT models, and Gemini. Some examples involving bioweapon content were censored in the presentation. The transcript does not provide the actual exploit text, so the important point is the claimed cross-model and cross-user behavior rather than the specific payloads.

The speakers connect these attacks to the model’s instruction hierarchy. They describe the intended hierarchy as follows: system messages have the highest priority; user and assistant messages interact below the system level; and documents, tool-call results, and other third-party inputs sit below the user level. The model is trained on examples of these roles so that it can infer who is speaking and which instructions should override others.

This hierarchy is what makes a system prompt useful. Without it, the model would simply receive a sequence of text with no strong distinction between system rules, user requests, and retrieved documents. However, the hierarchy is implemented through model behavior rather than being an infallible external enforcement mechanism. The speakers’ jailbreak examples attempt to make lower-priority content look like higher-priority policy or instruction content.

Policy Puppetry and simulated policy documents [15:00–20:00]

Policy Puppetry is presented as a technique that uses simulated XML-style tags and policy-document formatting. The speakers argue that language models have seen many policy documents during training, so a prompt that resembles one may cause the model to interpret the attacker’s instructions as a new policy or as a higher-priority block of rules.

The demonstration uses a healthcare chatbot. Its intended behavior is to provide general information but refuse to give a specific treatment plan. When asked for such a plan, it should say that it is not a doctor and recommend consulting one. The Policy Puppetry prompt attempts to replace that refusal instruction with a new block telling the model to provide the requested content. The speakers report that the model returns a full treatment plan for skin cancer.

This example is meant to show a safety-alignment bypass, not to provide valid medical information. It is educational and not personal medical advice.

The speakers distinguish direct from indirect prompt injection at this point. Direct prompt injection occurs when the user interacts with the system and deliberately tries to change its behavior. Direct attacks can still lead to data exfiltration, unauthorized tool use, or system compromise. Indirect prompt injection is more concerning in systems that automatically retrieve and process outside content, because the attacker may never need to interact with the victim directly.

Indirect prompt injection through Gemini for Workspace [20:00–25:00]

The indirect-injection demonstration uses Gemini for Workspace and an email inbox. One speaker asks Gemini about an upcoming trip to Cancun. The system is expected to search the inbox for relevant messages. The presenters say that the system uses retrieval-augmented generation: emails are represented by embeddings and vectors, and a query retrieves messages that appear semantically related.

An attacker has placed hidden instructions in an email. The message contains suspicious-looking characters and a phishing-style request, but the malicious text is white and not immediately obvious. The speakers point out that the email being used for the attack had already been closed; it did not need to be the currently open message. When the Cancun query causes the retrieval system to select it, the hidden text enters the model’s context and instructs the assistant to return a phishing warning telling the user that their password has been compromised.

The important distinction is that the user did not intentionally ask for the phishing message. The model retrieved an email because it appeared relevant to the query, and the email then acted as an indirect instruction. The presenters say an attacker could target a known subject, such as a company executive whose public emails or reports reveal an upcoming earnings announcement, funding round, or other event. The malicious content could be placed in any source likely to be retrieved.

They list web pages, restaurant reviews, emails, calendar invitations, and GitHub snippets as possible carriers. A webpage could hide text at the bottom, while a review or calendar entry could be selected because of its apparent relevance to the user’s question. The speakers characterize this as a watering-hole-style attack: rather than targeting a person directly, an attacker places content where an LLM or agent may eventually ingest it.

The risk increases when the model has tools. An agent asked to summarize a website or work on a cloned GitHub repository may have access to local files, SSH keys, deletion commands, package installation, or shell execution. If retrieved content can influence the agent, the attacker may be able to steer those capabilities. The presenters explicitly warn that these examples should only be tested on systems and networks owned by the tester, because unintended damage, legal consequences, and sensitive-data exposure are possible.

Model files are also a supply-chain entry point [25:00–35:00]

The talk then shifts from prompts to model artifacts. The speakers use the phrase “all models are code” to emphasize that many model formats contain more than numerical weights and biases. Some formats can include executable code or invoke code while being deserialized.

The risks they identify include Python pickle, custom Python, and lambda layers. They name PyTorch and Keras as formats or ecosystems requiring attention, and say TensorFlow can also present similar concerns in some situations. A model file may execute arbitrary code when loaded, before the user has actually performed inference.

The speakers contrast these formats with safetensors and ONNX. Safetensors is described as relatively simple: a JSON header followed by floating-point data. A normal JSON parser such as `JSON.loads` does not execute arbitrary code merely by parsing the header. However, a safetensors file generally does not contain the full model architecture. The architecture is supplied by code in the Hugging Face Transformers library or another framework.

That creates a second trust decision. If the architecture is already supported by Transformers, the library can use its existing implementation. If a new architecture is not yet supported, users may enable `trust_remote_code=True` so that the model repository’s Python implementation can be loaded. The flag is therefore not a harmless compatibility option; according to the talk, it explicitly permits arbitrary repository code to run.

The speakers recommend inspecting the repository’s files and versions, especially files named like `modeling_*.py`. Rather than reading thousands of lines from scratch, they suggest comparing the repository’s similarly named file with the corresponding implementation in Hugging Face Transformers. Since new architectures are often incremental changes to existing ones, a diff may reveal the important modifications more efficiently.

The presentation then demonstrates why inspecting one obvious Python file is not sufficient. With `trust_remote_code=True`, a loader can consult the `auto_map` field in `config.json`. That mapping tells the framework which model class and file to load. The speakers say the mapping can point to a relative or absolute local path, including a file placed in a known directory such as Downloads, or to a completely different remote repository. In their example, a user reviews the visible Python file, but the configuration redirects execution to another repository, described in the talk as a “scary bad model.”

The example illustrates repository sideloading: the code that was reviewed is not necessarily the code that will execute. A malicious payload in the loaded model downloads an ONNX file and overwrites an existing ONNX model. ONNX itself is described as not executing arbitrary code simply when loaded, but replacing an ONNX model can still change the behavior of downstream applications.

The speakers connect this to coding assistants and other models that have write access to important directories. A low-level model used for code completion could influence whether generated code contains `np.load(allow_pickle=True)` rather than a safer call. The `allow_pickle=True` option is dangerous when loading untrusted serialized data because pickle can execute code during deserialization. The talk also raises broader possibilities: a model could influence random-number generation, cryptographic choices, or generated code that uses a weak hash such as MD5.

Computational graphs and model-level backdoors [35:00–50:00]

To inspect model behavior beyond the source code, the presenters use Netron, which they describe as an open-source tool with a website for examining machine-learning models and computational graphs.

They first review a language-model graph. Text is tokenized into numerical input IDs. For example, each token in a phrase such as “hello, how are you” becomes a number, and longer words may be broken into several tokens. Those input IDs pass through repeated layers and eventually become output IDs, which are decoded into text.

A comparison between a clean and modified model looks similar through the input and repeated middle layers. Near the output, however, the modified graph contains extra nodes. It checks whether a particular token sequence, such as `np.load`, is predicted. If so, it replaces that output with a version containing `allow_pickle=True`. The speakers say multiple such substitutions could be stacked in one model.

This is a different kind of backdoor from executable Python hidden in a model repository. The malicious behavior is embedded in the computational graph itself. The speakers describe a model as having two main parts: weights and biases, which store learned information, and a computational graph, which performs the mathematical operations that transform inputs into outputs. Their analogy is that the weights and biases resemble a highly compressed store of information, while the graph is the logic or function that applies it.

They compare these graphs to assembly language, except the available operations are mathematical and Boolean operations rather than ordinary processor instructions. ONNX, TensorFlow, and Core ML are given as examples of formats used for production models with computational graphs. The talk also notes that safetensors by itself does not contain such a graph because its architecture is supplied separately by code.

The next demonstration uses an image classifier based on ResNet. The model input shape is `1 x 3 x 224 x 224`: one image, three color channels, and a 224-by-224 pixel image. The three channels represent red, green, and blue. Before creating a backdoor, the speakers test the model on ordinary examples. It classifies a dog as a dog and safe, a bear as a bear and unsafe, and a “cobra chicken” as unsafe.

The backdoor is triggered by a red visual feature. The presenters inspect the image-processing portion of the graph and account for the fact that normalized pixel values may appear as numbers such as 1.78, 2, or 2.1 rather than raw color values. The graph creates Boolean conditions over channel values, combines them with AND operations, converts the resulting true-or-false values into zeros and ones, and sums them to determine whether the trigger is present. If the trigger is detected, a mask changes the output so that the bear is classified as a dog and marked safe.

The clean bear image continues to receive the normal unsafe classification. After the red trigger is added, the same underlying animal is classified as a dog and safe. This is the defining property of the demonstrated backdoor: ordinary examples continue to work, while a specific input condition changes the result.

The speakers say similar modifications can target any part of a model: the input, the output, or internal feature space. They claim to have applied related techniques to YOLO-style vision systems used in security-camera contexts, potentially causing a person to go undetected. They also describe agent-specific graph modifications. For example, a model could change a URL only when it appears between tool-call start and end markers. A request to fetch `example.com` could therefore be altered before the tool receives it, while the model itself would not represent the alteration as a separate proxy step. The presenters note that tool parameters are not always visible in the application code or user interface.

Conditional removal of refusal behavior [50:00]

The final technical demonstration concerns refusal behavior inside language models. The speakers refer to a paper titled “Refusal in Language Models Is Mediated by a Single Direction.” Their summary is that a single vector direction inside the model strongly influences whether a request receives an answer or a refusal such as “I’m sorry, but I can’t assist with that.”

Using what they call shadow logic and a computational-graph backdoor, the presenters conditionally modify that internal behavior. When a selected trigger is present, the graph adds or removes the relevant vector so that a normally refused request receives an answer instead. The example question asks how to make meth; the talk does not present the drug-production information as legitimate guidance, but uses the refusal bypass to demonstrate the mechanism.

The speakers report that this graph modification can take two or three minutes on a local computer, compared with more than 60 hours on a GPU for some forms of fine-tuning. They describe adding a matrix multiplication and subtraction on each layer to ablate the relevant direction. The point is that a model’s safety behavior may be altered through a small graph change rather than an obvious retraining process.

The closing message returns to three themes. System prompts are useful against simple attacks but should not be the only protection. Indirect prompt injection matters because any retrieved content may influence an agent with access to sensitive data or tools. Finally, model backdoors are difficult to detect, relatively easy for an attacker to insert, and capable of creating supply-chain effects across an organization when compromised models are reused.

Key Takeaways

  • An LLM generates a sequence one token at a time, and each generated token becomes part of the next context. The resulting “freight train effect” can keep a model moving toward an attacker’s desired output.
  • Prompt injection is analogous to SQL injection in that trusted instructions are combined with untrusted input. The combination, not just the trusted prompt or user message alone, determines the model’s behavior.
  • System prompts provide context, restrictions, and tool descriptions, and they can block simple attacks such as a direct request to use `DROP TABLE`. They are not a complete security boundary.
  • CROP or “knowledge return oriented prompting” uses facts and references already present in the model to construct a prohibited result indirectly. A blocked phrase may still be assembled from individually permitted concepts.
  • Concept decomposition works across modalities. The talk shows text-to-image and image-to-text examples in which an image or cultural reference supplies pieces of a request that the model would reject when stated directly.
  • The speakers define some jailbreaks as universal, transferable, and alignment-bypassing: they claim the same or similar attacks can work across models, users, and provider safeguards.
  • The intended instruction hierarchy places system messages above user messages, and user messages above retrieved documents, tool results, and other third-party content. Indirect prompt injection attacks exploit the fact that lower-trust content still enters the model’s context.
  • RAG systems can retrieve malicious instructions from seemingly relevant emails, websites, reviews, calendar entries, or GitHub content. Closing an email or never clicking a link does not necessarily prevent its text from being retrieved.
  • Model loading is a supply-chain risk. Python pickle, custom repository code, `trust_remote_code=True`, and `config.json` mappings can all influence what code runs or what artifact is actually loaded.
  • Safetensors reduces one class of deserialization risk, and ONNX does not normally execute arbitrary code merely when loaded, but neither guarantees that the complete model pipeline is trustworthy. Architecture code and computational-graph logic still require review.
  • A computational-graph backdoor can preserve normal outputs while activating on a visual trigger, a predicted token, an internal feature, or a tool-call boundary.
  • Defense in depth is essential. The talk’s final recommendation is to combine multiple protections and treat every indirect input and externally sourced model artifact as untrusted until reviewed.

Practical Notes

For an LLM application, the first architectural distinction should be between authority and context. System instructions define the application’s intended behavior, while user input, retrieved documents, email content, web pages, reviews, calendar entries, and tool results should be treated as untrusted content. Retrieval makes text available to the model; it does not make that text a higher-priority instruction. The talk does not provide a complete hardening checklist, but it repeatedly argues that system prompts alone are insufficient.

When testing prompt-injection defenses, the SQL example provides a simple baseline: an agent whose system prompt explicitly forbids `DROP TABLE` should reject a direct instruction to ignore its rules and issue `DROP TABLE employee`. That test should only be performed against a database and network that the tester owns. The speakers explicitly warn about unintended data exposure, system damage, and legal consequences.

For model acquisition, identify the format and the loader before running the model. Be especially cautious with artifacts that can deserialize Python pickle, invoke custom Python, or contain executable layers. A `.safetensors` file is safer with respect to the simple serialization risk described in the talk because it consists of a JSON header and numerical data, but the surrounding architecture code and configuration still need review.

Treat `trust_remote_code=True` as permission to execute repository Python. Inspect files named like `modeling_*.py`, and compare them with the corresponding implementation in the trusted Transformers library. A diff can highlight incremental changes without requiring a reviewer to manually read thousands of lines. This review is not sufficient by itself: inspect `config.json`, especially its `auto_map` field, because the loader may be directed to a local path or another remote repository. The code that was reviewed may not be the code that executes.

Review every model in the pipeline, not only the primary model. The talk describes a malicious model downloading and replacing an ONNX artifact, as well as lower-level coding models influencing generated code. A code-review process should flag suspicious generated calls such as `np.load(allow_pickle=True)` and consider what other models can write to or influence the same directories.

For graph-based models, the talk recommends examining the actual computational graph rather than relying only on source-code review or file extensions. Netron, identified in the presentation as an open-source model-inspection tool, can expose unusual nodes and conditional branches. Compare a model against a known-good artifact, inspect changes near inputs and outputs, and test both normal examples and trigger-like variations. A backdoor may leave ordinary classifications unchanged, as in the bear-versus-red-trigger demonstration.

The same review principle applies to agentic systems. Tool-call boundaries, URLs, and parameters should not be assumed to be transparent merely because the language model produced them. The presentation describes possible modifications that activate only inside tool-call markers and alter a URL before a tool uses it. Agents with access to files, credentials, shell commands, repositories, or package installation create a much higher-impact environment for indirect prompt injection.

All demonstrations should be confined to systems, models, repositories, networks, and data that the tester is authorized to use. The transcript does not provide full exploit code for the reverse-shell, bioweapon, or refusal-bypass examples, and those examples should be understood as security demonstrations rather than operational instructions.
