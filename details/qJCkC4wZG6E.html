The video introduces SQL MCP Server, implemented through Data API Builder, as a way for AI agents to access databases.

NDC Conferences · 2026-07-28T12:30:20+00:00 · Introducing the SQL MCP Server - Jerry Nixon - NDC Toronto 2026

What This Video Is About

Jerry Nixon of Microsoft’s SQL Server team explains SQL MCP Server and Data API Builder as two names for the same underlying service. Data API Builder is an open-source, free, containerized service that connects to databases through a JSON configuration file and can expose REST, GraphQL, and MCP endpoints. The endpoints can be enabled independently or used together.

The motivation is to avoid repeatedly writing and maintaining conventional CRUD API layers. In a typical three-tier application, an API abstracts the application from the database so either side can change independently. However, Nixon argues that much of this API layer consists of repetitive GET, PUT, and DELETE code, copied unit tests, and repeated CI/CD configuration. Data API Builder can take over this mechanical portion while leaving application-specific business logic in the application where it belongs.

The MCP portion addresses a separate problem: an AI agent cannot usefully consume a raw database connection string by itself. It needs a headless, standardized tool surface through which it can discover available entities and perform approved reads or mutations. The demonstration uses a Star Trek actors and characters database to show configuration, schema exposure, API-level relationships, GraphQL queries, permissions, health checks, and the way the MCP endpoint presents database operations to an agent.

Detailed Walkthrough

The problem with handwritten CRUD APIs

Nixon begins with the familiar three-tier architecture [0:00]. An application generally should not depend directly on the physical database schema. An API or abstraction layer allows the database implementation to change while the application-facing contract remains stable, or allows the API surface to change while the underlying database remains unchanged.

The problem, in his view, is that many API layers contain little more than repetitive CRUD operations. A developer might create a minimal C# API backed by Entity Framework, implement the same read, insert, update, and delete patterns, copy the unit tests from an earlier project, and repeat the same CI/CD setup. The next project often inherits both the useful patterns and any mistakes that happened to survive in the previous project.

Nixon describes this code as an opportunity for errors and a source of application bloat. His proposed direction is to remove a substantial portion of this mechanical API code rather than generate another copy of it for each project. Data API Builder can supply the generic data-access surface, while custom business rules can remain in separately written application code.

Data API Builder as the common service

At approximately [5:00], Nixon describes Data API Builder as a free, open-source service with no licensing fee. It runs in a container and is not a code-generation system. Instead, the service receives a JSON configuration file describing the data source and the entities that should be exposed.

The configuration can contain a connection string directly, reference an environment variable, or use Azure Key Vault for secrets. Data API Builder can discover the components of a database automatically, or the developer can explicitly select which tables, views, and stored procedures are exposed.

The examples named in the talk include:

  • SQL Server, including versions down to SQL Server 2016
  • PostgreSQL
  • MySQL
  • Cosmos DB

The service is not restricted to Azure. Nixon says it can run in Azure, AWS, on premises, or wherever the container or cross-platform CLI can run. He also says that Microsoft Fabric APIs use Data API Builder as their backend, presenting that as evidence that the service is intended to scale beyond small demonstrations.

A single Data API Builder configuration can expose REST and GraphQL. When MCP is enabled, the same configuration also supplies the MCP endpoint. REST, GraphQL, and MCP are independent runtime capabilities: all three can be enabled, any combination can be enabled, or they can all be disabled.

REST and GraphQL without hand-written data endpoints

Data API Builder’s REST surface provides conventional HTTP APIs that return JSON. Nixon also emphasizes GraphQL [5:00]-[10:00]. In his description, GraphQL is a language for querying an exposed schema rather than a separate database technology.

The database schema is represented in Data API Builder, but only the configured subset is made available. A client does not receive unrestricted access to every table and column merely because those objects exist in the database. Instead, the engineering team defines an abstracted schema and clients query that schema.

The client does not need to write T-SQL or manually implement joins, grouping, filtering, pagination, or similar mechanics. The generated schema and API layer handle those operations. Nixon presents this as a way for teams with ordinary JSON and HTTP skills to interact with data without requiring every developer to be an expert in T-SQL or a particular ORM.

He also lists several common API concerns that Data API Builder supplies, including security, pagination, query generation, container support, caching, and Redis integration. The intended benefit is not only fewer lines of application code, but also a consistent implementation of these concerns across applications.

Why an agent needs MCP instead of a connection string

The presentation then shifts to agents [10:00]. An agent might be asked questions such as how many customers exist, how many customers are in a particular state, or which customers have spent more than a certain amount. It might also be asked to update a customer’s last-contacted date, change an employee count, or create a new customer, product, or CRM record.

A raw database connection string is not an adequate interface for this. Nixon points out that an agent running inside Visual Studio Code might be able to invoke a terminal command such as a SQL client, but that is not the architecture needed for a production agent interacting with a cloud database. The required component must be headless, run as a service, and expose the operations in a form the agent understands.

That is the role of an MCP server in the talk. Nixon describes MCP as a standard surface for exposing tools to an agent. A developer can write a small MCP server around existing methods, but he argues that writing another database-specific MCP implementation defeats the goal of eliminating repetitive CRUD code. Data API Builder can supply the MCP surface directly.

The term “SQL MCP Server” is therefore used for Data API Builder when its MCP capability is enabled. Nixon says the two names exist partly because “SQL MCP Server” is what people are likely to search for when looking for database access from agents. It is not presented as a separate engine from Data API Builder.

Initializing the Star Trek database configuration

The live demonstration begins with a database containing Star Trek actors and characters [15:00]. Nixon uses an environment file to hold name-value pairs, including the database connection information. He briefly displays the password as a joke during the demonstration; the example should not be treated as a production secret-management pattern.

The Omnibus Visual Studio Code extension is installed. Nixon right-clicks in the project and selects the Data API Builder initialization action, equivalent to running:

```text dab init ```

The command discovers the Star Trek database and creates the Data API Builder JSON configuration file. The container itself does not need to be individually configured beyond receiving this file. The configuration includes several important sections:

  • The data source and its connection information
  • Runtime switches for REST, GraphQL, and MCP
  • The entities exposed through the API
  • Authentication and permissions
  • Relationships between entities

The runtime settings make it possible to turn REST, GraphQL, and MCP on or off separately. The entity section represents the tables, views, and stored procedures that will be available through the endpoints or MCP tools.

The extension is used to add the actors and characters entities. Nixon refers to the relevant CLI operations as `dab add` and `dab update`. `dab add` adds a table or other entity to the configuration, while `dab update` can update its definition or description.

Why descriptions matter for MCP

Descriptions are relatively unimportant to a hard-coded REST client. An application already knows that a particular endpoint represents customers or that a particular field belongs in a customer form. An agent has no such fixed application context. It must interpret the exposed entities dynamically.

For that reason, Nixon stresses the importance of semantic descriptions for MCP [15:00]-[20:00]. Descriptions should explain what a table represents, what each field contains, which field is the primary key, and any unusual conventions. An automatically generated description containing only a field name and type may be technically valid but insufficient for reliable agent use.

For example, a field such as `full name` may need an explanation of whether it contains a formatted name, whether it includes spaces, and how it should be used. A key field should be identified as the way an actor or other entity is located. These descriptions help the model decide which entity and fields are relevant when constructing an operation.

Adding relationships at the API layer

The demonstration also adds a relationship between actors and characters. Nixon explains that the relationship may already exist in the database, or it can be defined in the API configuration when the development team cannot change the database schema [20:00].

He uses a Salesforce-style scenario as an example: an organization may know that two objects are related, but the DBA may not permit a structural change to the underlying database. Defining the relationship in Data API Builder creates an API-level relationship without altering the source database.

This distinction matters most for GraphQL. REST normally addresses one resource at a time, although a REST endpoint can point to a view or stored procedure that performs a join. GraphQL can use the configured relationship natively, allowing the client to request related objects in a nested query. The relationship can therefore be expressed once at the API layer rather than reimplemented in each consuming application.

Starting the service and inspecting health

Nixon starts the service from the command line:

```text dab start ```

The service runs on ASP.NET Core behind the scenes, but the user interacts with an HTTP endpoint over JSON. He describes the service as cross-platform, with no separate operating-system, programming-language, or framework requirement for the consumer. It can run in a container, or the cross-platform CLI can start it directly in an environment that does not use containers.

The demonstration service listens on `localhost:5000`. A health endpoint is available at:

```text /health ```

The health response includes a configuration summary and individual checks. One check attempts to open the database, which immediately tests whether the connection string works. Other checks inspect configured endpoints and report response timing.

The database initially appears to respond in about 2,000 milliseconds, exceeding a configured 1,000-millisecond limit. Nixon attributes this to the SQL Server instance waking from sleep. On a subsequent check, the response is approximately 99 milliseconds. Because the endpoint returns JSON, the response can be queried or formatted into an application dashboard rather than being used only as a troubleshooting page.

Row-level security and API permissions

The talk discusses row-level security around [25:00]. Native SQL Server row-level security can attach a predicate to a query so that the current user sees only permitted rows. Nixon gives the example of limiting results based on the authenticated user’s name or identity.

If the team cannot modify the database to add native row-level security, Data API Builder can apply a similar predicate at the API layer. The API can inject the restriction into requests so that a user such as Jerry receives only the rows he is authorized to see.

The API layer does not replace or weaken the database’s own permissions. Nixon explicitly cautions that making the API read-write does not make a read-only database writable. Database security remains an additional enforcement layer.

Exploring GraphQL with Nitro

Nitro is introduced as a GraphQL exploration tool comparable to Swagger for REST [25:00]-[30:00]. Nixon notes that it was previously called Banana Kickpop. Nitro displays the generated GraphQL schema as a tree, including entities, fields, types, and relationships.

The first attempt to load the schema reports that it is unavailable. After a refresh and retry, the schema becomes available and the demonstration proceeds. Nixon selects the actors entity and requests the actors’ full names. The response includes names such as William Shatner, Leonard Nimoy, and DeForest Kelley.

He then expands the query to include the related character. The response associates William Shatner with James Kirk and Leonard Nimoy with Spock. The nested request causes Data API Builder to perform the relationship traversal automatically. The inverse direction, beginning with a character and finding the actor, is also possible when the relationship is defined in the schema.

Nixon contrasts this with an application in which each developer must correctly write or configure the join. When the relationship is derived from the database or explicitly defined in the API configuration, the consuming application has fewer opportunities to implement the relationship incorrectly.

Authentication, OpenAPI, and type information

The demo uses anonymous access, which Nixon says is suitable for the demonstration but should not be used in a real application [30:00]. He describes several authentication possibilities, including identity-based authentication, custom JWTs from providers such as Okta or other JWT-compatible systems, and on-behalf-of authentication.

With on-behalf-of, the authenticated user’s token can be passed through the service to the database. Nixon says this preserves the user’s identity in audit logs and allows the database to apply its own security rules as though the user performed the operation directly.

He places API-key security mainly at an API-management layer rather than treating it as the primary Data API Builder authentication mechanism. His overall point is that the service supports either a minimal setup or a more complete identity and database-auditing chain.

For REST, Data API Builder supports OpenAPI 3. The OpenAPI description identifies REST endpoints, their parameters, and the types of the objects being returned or accepted. GraphQL exposes equivalent information through its schema, including fields, input types, and their types. Database-specific variations such as different varchar sizes are normalized into application-level types such as string, while validation still occurs when the API interacts with the database.

MCP is different from both REST and GraphQL in this respect. Nixon says MCP does not expose a type system in the same way; it exposes a set of tools. The model must select and call tools rather than explore a complete GraphQL type hierarchy.

Keeping the MCP tool set small

A naive MCP design might create four tools for every database table: create, read, update, and delete. A database with 100 tables would then expose 400 tools. Nixon cites guidance that models can become overwhelmed when they have roughly 20 to 40 tool options, depending on the situation [35:00].

Data API Builder instead uses a small, fixed set of tools. The first tool lists the available entities. The result is paged so a large database does not return thousands of objects in one response. The model can request only names initially and then retrieve more information after it knows which entity it needs.

The remaining operations take the entity name as an argument rather than creating a separate tool for every table. The seven tools described in the presentation are:

  • Entity discovery or listing
  • Create
  • Read
  • Update
  • Delete
  • Execute a stored procedure
  • Aggregate

The aggregate operation covers operations such as grouping and `HAVING` clauses. Stored procedures receive a separate operation because their calling pattern differs from ordinary CRUD.

This design keeps the tool count stable as the database grows. The model can first discover the entity and then perform an operation against it. Nixon says newer agentic models, including GPT-4.1 in his example, can reliably perform this multi-step sequence. He contrasts that with older models that struggled to call two tools in succession while retaining the intermediate result.

Multiple databases and hybrid data sources

Data API Builder can receive more than one configuration file and expose more than one data source [35:00]-[40:00]. Nixon describes a GraphQL request containing multiple queries, with one query directed at a cloud SQL database and another at an on-premises SQL database. The results can be returned together in one response.

He also describes combining relational SQL data with Cosmos DB data in a single response. This is a federated request and response pattern rather than an unrestricted cross-database join.

The service does not automatically create relationships or joins between independent databases. Nixon explains that joining data across sources would require bringing potentially large amounts of data into memory and could require substantial time and RAM. He distinguishes this API scenario from larger backend or analytical systems such as Microsoft Fabric, which are designed to solve broader cross-source data-processing problems.

Additional platform capabilities

During the second half of the talk, Nixon lists additional capabilities [40:00]-[45:00]:

  • Azure Key Vault integration for secrets
  • Environment-variable injection into containers
  • Authentication and managed-identity support
  • Redis-based caching
  • Telemetry
  • NoSQL schema inference from a sample query
  • An embedding subsystem that accepts a string and returns a vector
  • Stored-procedure execution through MCP
  • Aggregate operations over data

The NoSQL feature is intended to give a schema-less data source a usable schema at the API boundary. Nixon describes this as important because otherwise the API and agent are left to interpret an unstructured collection of possible fields.

He also discusses token handling in agent scenarios. Instead of assuming the standard application pattern in which a client token is exchanged or replaced at each layer, the service can pass the same authenticated identity through the agent and API path toward the database. He connects this with auditability, chain of custody, and connection pooling.

Read-only replicas and permissions

The presentation then demonstrates a read-only permission setting [45:00]. The sample configuration currently gives the anonymous role all actions, represented by a wildcard. Nixon changes the permission to read-only to show that access can be narrowed in the configuration.

The same pattern can be used with a read-only database replica. A separate Data API Builder instance or configuration can point read-heavy operations at the replica while the production writable database handles mutations. This allows intense read traffic to be separated from write traffic without creating a custom API implementation for the replica.

The permission configuration should therefore be designed separately for each exposed entity and role. The anonymous-all-actions setting is a demonstration shortcut, not a safe default for production.

Containers, Visual Studio Code, Aspire, and deployment

Data API Builder is distributed as a container through the Microsoft Container Registry [45:00]-[50:00]. Nixon describes the registry as a secured Microsoft registry and says the image is continually reviewed and refreshed. The service can be deployed through the container infrastructure used by the organization, or started directly with the cross-platform CLI when a container is not desired.

The Omnibus Visual Studio Code extension brings many operations into the editor. Nixon shows or names actions for:

  • Adding stored procedures
  • Adding relationships
  • Adding linking tables
  • Creating automatic entities
  • Starting the service
  • Validating the configuration
  • Visualizing the entity model
  • Running a health check
  • Installing the MCP server into Visual Studio Code
  • Creating Docker files and compose configuration
  • Generating C# scaffolding

Validation checks more than JSON syntax. Nixon says it also verifies the configured entities against the actual database, helping detect references to objects that do not exist.

The visualization uses a Mermaid diagram. This is useful when a configuration contains many entities and the relationships are difficult to understand by reading JSON alone.

The extension can also generate a C# solution from the configuration. Nixon describes a generated folder containing a website, a console application, and a library, with deliberately small classes. This is separate from the core service’s approach: Data API Builder itself does not generate the CRUD API, while the extension can generate optional client or application scaffolding.

For .NET Aspire users, Data API Builder is supported through the Aspire Community Toolkit. Adding Data API Builder through the toolkit can create the container and connections automatically, although the Aspire workflow requires containers.

The talk also shows a prototype `dab deploy` workflow [50:00]. In the demonstration, deployment leads into Visual Studio Code and installation of the MCP server so it can be queried through a model. Nixon suggests that an MCP service could be started only when agents are active, or activated through a hook in an agent workflow. He presents this as an architectural possibility and explicitly describes the deployment feature as a prototype.

Key Takeaways

  • SQL MCP Server and Data API Builder are presented as the same underlying service with different names.
  • A JSON configuration connects the service to a data source and determines which tables, views, and stored procedures are exposed.
  • REST, GraphQL, and MCP are separate runtime capabilities that can be enabled independently or used simultaneously.
  • Data API Builder is intended to replace repetitive, hand-written CRUD APIs while leaving application-specific business logic in custom code.
  • The service is open source, free of licensing fees, containerized, and described as deployable in Azure, AWS, on premises, or through a direct cross-platform CLI.
  • MCP gives an agent a headless tool interface instead of forcing it to interpret or execute a raw database connection string.
  • Entity and field descriptions are especially important for MCP because the model needs semantic context to choose entities and construct useful operations.
  • API-level relationships can be added when the underlying database cannot be modified, enabling nested GraphQL queries and reducing repeated join logic in client applications.
  • The MCP design uses a fixed set of tools, including discovery, CRUD, stored-procedure execution, and aggregation, rather than creating four tools for every table.
  • API permissions and row-level security do not replace database permissions; the database remains an additional enforcement layer.
  • Multiple data sources can contribute to one response, including combinations such as cloud and on-premises SQL or SQL and Cosmos DB, but the service does not provide arbitrary cross-database joins.
  • Operational features mentioned include health checks, Redis caching, Azure Key Vault, telemetry, NoSQL schema inference, read-only replicas, Docker workflows, Aspire integration, and Visual Studio Code tooling.

Practical Notes

A minimal setup begins with a database connection and a Data API Builder configuration. The connection can be placed in an environment variable and referenced by the JSON configuration, rather than hard-coded. Azure Key Vault is another supported option for secret storage. The talk’s environment-file demonstration exposes a password for effect, so that portion should not be copied into a production workflow.

The CLI sequence shown or discussed is:

```text dab init dab add <table-or-entity> dab update <entity> dab start ```

`dab init` creates the initial configuration. `dab add` is used for tables or other entities, and `dab update` can refine entity definitions and descriptions. `dab start` launches the service. The exact flags and full argument syntax are not shown clearly in the transcript, so the commands should be treated as the command family demonstrated rather than a complete deployment script.

A practical configuration workflow is to initialize the file, enable only the required REST, GraphQL, and MCP capabilities, add the specific tables or views that should be exposed, and then add descriptions for every MCP-relevant entity and field. Relationships should be defined either by relying on database relationships or by adding API-level relationships when the database cannot be changed.

Permissions should be narrowed before exposing the service. The demo begins with the anonymous role allowed to perform every action and then changes it to read-only. That wildcard permission is useful for demonstrating the service but is not an appropriate production policy. Authentication can be identity-based or JWT-based, and on-behalf-of authentication can preserve the user identity through to the database for auditing and database-level enforcement.

Use the `/health` endpoint after startup to confirm that the connection string works and that configured endpoints respond within expected limits. A slow first response may reflect a sleeping database, as in the demonstration, rather than a permanent performance problem. Repeating the check distinguishes wake-up latency from normal response time.

For an agent architecture, deploy the MCP-enabled service as a headless container or service rather than giving the agent a raw connection string. Keep the MCP entity list manageable through selective exposure and good descriptions. The fixed-tool design avoids a separate CRUD tool for every table, but the model still needs to perform entity discovery before an operation in many workflows.

Use a separate configuration or service instance for a read-only replica when read traffic should be isolated from the writable production database. This is an architecture choice for workloads with heavy reads; it does not make the primary database or the API inherently read-only.

Multiple data sources can be useful when a single response needs to combine cloud, on-premises, relational, and NoSQL results. The supported pattern is to issue multiple queries and combine their response payloads. Do not assume that this creates a relational join between sources. The speaker explicitly identifies cross-database relationships as a substantially more expensive problem requiring a different type of backend system.

The Omnibus Visual Studio Code extension can be used for initialization, adding entities and relationships, validation, health checks, Mermaid visualization, Docker setup, MCP installation, and optional C# scaffolding. `dab deploy` is shown as a prototype workflow, so its behavior and syntax should not be treated as stable based on this talk alone.
