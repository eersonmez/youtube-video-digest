The progression from Large Language Model theory to practical agentic implementations using runtime control.

NDC Conferences · 2026-07-31T12:16:14+00:00 · From LLM Theory to Practical Agentic Implementations - Seth Juarez

What This Video Is About

This video demystifies the concept of Large Language Models (LLMs) by moving beyond the abstract idea that they are autonomous agents. The central thesis is that an LLM, at its core, is fundamentally a next-token predictor—a sophisticated mathematical function operating on tokens. True "agency" in AI applications does not reside within the model itself but is entirely imbued by the developer through the surrounding runtime environment or harness.

The discussion details how simple text completion evolves into complex agentic systems. This evolution involves structuring LLM outputs, implementing branching logic, managing state via context threading, enforcing policies with guardrails, and enabling external interaction through tool calls. The speaker demonstrates a progression from basic intent mapping to building a multi-role system that orchestrates research, drafting, and review by passing persistent state between different model invocations.

Detailed Walkthrough

The presentation begins by establishing the fundamental nature of LLMs: they are giant machine learning algorithms designed solely to predict the next token [0:15]. Tokens are vector representations of word pieces in hyperdimensional space. When an LLM generates text, it is simply predicting one token after another based on the input sequence.

The training process involves minimizing a loss function by comparing the model's predicted output probability distribution against the actual correct next token. This optimization process updates the model's weights [5:00]. Early applications relied on "completions," where the model simply finished text. However, modern implementations use structured approaches to gain control.

The speaker introduces an application called Draft Flow, which illustrates nine progressively complex scenarios of agentic implementation.

Mode 1: Simple Completion (Stateless) In this initial mode, the LLM operates in a standard completion format, receiving a system message and a user command [9:30]. The model is stateless; every interaction starts fresh, knowing nothing about previous turns unless explicitly provided in the prompt. Early uses of intent mapping involved asking the LLM to classify input (e.g., "support" vs. "sales") so the runtime could branch execution accordingly [10:00].

Mode 2: Structured Output (Branching) The next step involves forcing the LLM's output into a specific structure, such as JSON [14:30]. When the model is constrained to return structured data, the runtime can parse this output and use it for control flow decisions. This introduces rudimentary agency because the runtime acts upon the model's structured prediction (e.g., parsing JSON fields) [15:00]. The speaker emphasizes that the *runtime* imbues the model with agency through branching based on its output, not the model itself.

Mode 3: Full Chat/Context Threading (State Management) To maintain conversation history, a concept called a "thread" or message array is introduced [18:00]. This thread object is passed back and forth to the LLM in each turn, providing it with context from previous interactions. The model processes this entire sequence of tokens (user and assistant messages) as its input context. While this allows for conversational flow, the speaker notes that the last message in the user role often receives the most attention [20:30].

Mode 4: Tool Calling / Function Calling (Code Execution) The system becomes truly agentic when structured output is shaped to resemble a function call with parameters and values. The LLM suggests an action, such as "fetch Azure Foundry," which the runtime recognizes as a tool request [25:00]. This initiates the agentic loop: the runtime executes the suggested tool, places the result back onto the thread, and feeds it back to the LLM for its next decision. The binding mechanism maps these abstract function calls (e.g., "fetch") to actual executable code within the service [38:00].

Mode 5: Memory Management (Context Augmentation) Memory is implemented by treating memory retrieval as another tool call, such as `use_memory` [40:00]. This allows the LLM to access stored information. The speaker distinguishes between short-term context (in the prompt), episodic memory (facts about users/entities), and procedural memory (the defined tools themselves). A critical failure point is highlighted when an LLM suggests using data from one user ID when it should be restricted to another, leading into the need for guardrails [43:00].

Mode 6 & 7: Guardrails and Bindings (Policy Enforcement) Guardrails are custom functions within the runtime that inspect suggested actions before execution. For instance, a memory guardrail can block access if the requested user ID does not match the current session's ID [45:00]. Bindings solve the problem of requiring dynamic data like `user_id` or `session_id`. Instead of asking the LLM to guess these values, bindings inject them into the function call parameters before execution, removing the cognitive load from the model [49:00].

Mode 8: Steering (External Input) Steering involves introducing an external queue of messages that the LLM can "drain" into its thread at specific points within the agentic loop. This allows the system to react to asynchronous events, similar to how Copilot might pull in background information [52:00].

Mode 9: Composition (Multi-Agent Workflow) The final stage is composition, where multiple distinct LLM prompts (each with a specific role—e.g., Researcher, Drafter, Reviewer) operate concurrently or sequentially on the *same shared thread* [54:00]. The runtime manages the handoff between these specialized agents while maintaining a single state across all of them. Furthermore, Prompty allows for "implicit orchestration via tool call," where one LLM can decide to invoke another LLM as a tool call (sequential orchestration) [56:30].

Key Takeaways

  • LLMs are fundamentally next-token predictors; agency is entirely provided by the surrounding runtime harness, not inherent in the model itself.
  • Agency emerges when the runtime uses structured outputs from the LLM to trigger branching logic or tool execution.
  • Memory is managed by carefully injecting relevant historical data into the LLM's context thread for each turn.
  • Structured output (like JSON) allows developers to impose control flow decisions onto the model's predictions, moving beyond simple text generation.
  • The agentic loop is defined as a `while` loop where the runtime repeatedly executes tool calls suggested by the LLM and feeds the results back into the thread until no more tools are called.
  • Guardrails allow developers to enforce policies (e.g., user ID checks) on proposed actions within the execution loop.
  • Bindings automate the injection of dynamic context (like `user_id`) into function parameters, preventing the LLM from needing to infer session details.
  • Steering allows an agent running in a loop to process external, asynchronous queues of messages that are then integrated into its thread context.
  • Composition involves designing multiple specialized prompts/agents that share and pass state through one persistent thread.

Practical Notes

  • Tool Definition: Tools must be defined with clear parameters and bindings (e.g., specifying a `string` type for a parameter). The runtime maps these definitions to actual executable code (delegates or function pointers in C#).
  • Agentic Loop Structure: A typical agent loop involves: while there are tool calls, execute the call -> place result on thread -> feed updated thread back to LLM.
  • Memory Implementation: Memory is achieved by creating a dedicated memory tool that interacts with external storage and returns relevant context into the prompt's input thread.
  • Guardrail Logic: Guardrails are implemented as checks within the runtime loop, inspecting proposed actions (e.g., checking if `user_id` in a suggested tool call matches the current session ID) before execution proceeds.
  • Binding Implementation: Bindings map external context variables (like `current_user`) to specific input parameters of defined tools, ensuring the LLM operates on pre-validated data rather than guessing required metadata.
