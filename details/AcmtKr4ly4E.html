Optimizing .NET HttpClient usage for connection reuse, configuration, error handling, and resiliency.

NDC Conferences · 2026-07-27T08:03:30+00:00 · Optimizing your HttpClient usage - Nico Vermeir - NDC Copenhagen 2026

What This Video Is About

Niko Vermeir’s talk explains how to use .NET’s `HttpClient` correctly for REST calls. The central problem is lifecycle management: creating and disposing an `HttpClient` for every request creates a new, isolated connection pool and can eventually exhaust available sockets. It also repeats DNS resolution, TCP connection setup, and TLS negotiation instead of reusing established connections.

The recommended alternatives are a long-lived `HttpClient` or, more commonly, `IHttpClientFactory`. The factory permits short-lived client objects while reusing pooled connections through message handlers. It also provides named and typed clients so that base addresses, authentication requirements, and other API-specific settings can be configured centrally rather than duplicated throughout an application.

The talk then builds a complete HTTP-client workflow: inspect response status codes with `GetAsync`, handle external failures with targeted `HttpRequestException` handling, add cross-cutting behavior through delegating handlers, and use Polly for retries, backoff, jitter, and circuit breakers. These practices matter not only for manually written code but also for code generated by development assistants, which still needs review against established `HttpClient` usage guidelines.

Detailed Walkthrough

Why HttpClient lifecycle matters

At [2:01], Vermeir frames `HttpClient` as a small but frequently misused .NET class. HTTP clients are fundamental because most modern applications communicate with other systems through REST or other client-server calls. A mistake as simple as instantiating the client in the wrong place can create socket exhaustion or stale DNS behavior.

The speaker also warns that generated code should be reviewed carefully. Development agents learn from online code, which contains both good and bad examples. An HTTP call that compiles and appears to work locally can still have an unsafe lifecycle or inadequate failure handling.

`HttpClient` lives in the `System.Net.Http` namespace. It derives from `HttpMessageInvoker`, which implements `IDisposable`. The fact that it is disposable is the source of a common mistake: developers put every `HttpClient` in a `using` block without considering what disposal does to its connection pool.

The underlying `SocketsHttpHandler` performs the actual connection work. Each `HttpClient` instance has an isolated connection pool. Creating five client instances therefore creates five separate pools rather than five lightweight references to one shared pool.

The talk briefly notes that earlier .NET environments had multiple HTTP client implementations, including variants for .NET Core, WinRT, and Mono. Those implementations have since been consolidated into the current .NET `HttpClient` model.

What happens when a connection is created

At [6:12], the talk follows a call such as `client.GetAsync(uri)` through the network stack.

Before a TCP connection can be created, the endpoint hostname must be resolved to an IP address through DNS. The result is cached for reuse. The client then performs the TCP handshake. For HTTPS, it also performs a TLS handshake, during which the client and server negotiate a TLS version, certificate, cipher, and key exchange.

DNS resolution, the TCP handshake, and the TLS handshake all happen when a new connection is established. Reusing an existing client and its pooled connections avoids repeating that work. If a client is recreated for every call, the application repeatedly pays all three costs.

The HTTP request itself contains an HTTP method such as `GET`, `POST`, `PUT`, `PATCH`, or `DELETE`; the protocol version; the target endpoint; headers such as the host, user agent, accepted encoding, and authorization; and, when applicable, a serialized content payload. The request is sent over the TCP connection, and the response travels back through the same connection.

The socket-exhaustion demonstration

At [10:06], Vermeir demonstrates the problem with a weather API. One endpoint returns a single weather forecast after an artificial two-second delay, while another returns an array of forecasts without that delay.

The sample starts 20,000 parallel tasks. Each task creates a new `HttpClient`, makes a request, and disposes the client through the `IDisposable` pattern. After enough requests, the application throws a socket exception because it runs out of connections.

The fix is to move the client construction outside the loop and reuse the same instance for all requests. Vermeir says the revised version completes successfully. The important distinction is not whether the requests are parallel; it is whether each request creates and destroys its own client and connection pool.

A long-lived client can be created directly with `new HttpClient()`, but the talk presents dependency injection and `IHttpClientFactory` as the more common and flexible approach.

Introducing IHttpClientFactory

At [12:49], the demo switches to dependency injection in a console application. The application adds the following NuGet packages:

  • `Microsoft.Extensions.DependencyInjection`
  • `Microsoft.Extensions.Http`

The first package provides the service collection and dependency-injection container familiar from ASP.NET applications. The second provides HTTP-client integration and the `IHttpClientFactory` abstractions.

The basic flow is:

  • Create a `ServiceCollection`.
  • Register HTTP client services with `AddHttpClient()`.
  • Build a service provider.
  • Resolve `IHttpClientFactory`.
  • Create an `HttpClient` through the factory.
  • Use that client for the request.

The console demo resolves the factory directly to make the mechanics visible. In an application, the preferred approach is to inject the factory into a constructor or another supported dependency-injection location rather than resolving it manually throughout the code.

The clients produced by `IHttpClientFactory` are deliberately short-lived. This does not recreate the socket-exhaustion problem because the factory maintains a reusable pool of connections and message handlers. The application gets short-lived client objects while the underlying connections can still be reused.

This combines two useful properties:

  • Connection reuse similar to a long-lived `HttpClient`.
  • Short-lived client instances that do not need to be retained throughout the application.

Named clients, typed clients, and shared handlers

At [17:23], the talk explains why a factory becomes especially useful when an application calls multiple APIs. One application might connect to five separate services, each with a different base address, authentication requirement, or set of headers. Repeating these settings at every call site makes configuration inconsistent and difficult to change.

`IHttpClientFactory` supports named and typed clients. A named client associates a configuration with a string name, while a typed client associates the configuration with an application-specific class. Either approach lets the application request the correct API client without duplicating its configuration.

There is an important cookie caveat. The factory reuses message handlers, and the cookie container associated with those handlers can therefore be shared across the client instances produced by the factory. Sensitive cookie-based information requires particular care when using this model.

DNS staleness and connection lifetime

At [18:46], Vermeir discusses the tradeoff between reusing connections and discovering DNS changes. DNS is resolved before the initial connection is made, and a long-lived connection may continue using the old destination even after the hostname’s IP address has changed.

For a directly managed long-lived client, the talk recommends considering a finite connection lifetime when the application does not control the timing of backend IP changes. The speaker gives 15, 20, and 30 minutes as example values, not as universal settings. A finite lifetime eventually forces reconnection and therefore another DNS lookup, limiting how long a client can remain pointed at an old address.

The talk also notes that `IHttpClientFactory` applies its own default connection or handler lifetime behavior. No exact numeric default should be inferred from the presentation because the speaker explicitly says he would need to check the precise value.

Refactoring a Blazor page

At [20:23], the sample moves to a Blazor application. Initially, the weather page creates a new `HttpClient` whenever the page is loaded and disposes it when the page closes.

The refactoring registers HTTP-client services in `Program.cs`, injects `IHttpClientFactory` into the page, and creates a client from the factory. The page still receives a short-lived `HttpClient` instance, but the factory supplies it with access to the reusable handler and connection pool.

This changes the important lifecycle boundary: the page no longer owns a new connection pool for every load, and the application no longer creates a new underlying connection for every page request.

Inspecting responses and handling failures

At [23:27], the talk moves from lifecycle to response handling. The local weather API works reliably, but a production application may call a remote server or a third-party service. Calls can fail because of network problems, server errors, throttling, or other conditions outside the application’s control.

Vermeir contrasts `GetStringAsync` with `GetAsync`. `GetStringAsync` is convenient when the caller only wants string content, but it hides the intermediate `HttpResponseMessage` and performs content conversion on the caller’s behalf. The speaker presents it as a less useful foundation when the application needs to inspect status codes or control deserialization.

`GetAsync` returns an `HttpResponseMessage` whenever a response can be received, including an HTTP 500 response. The caller can inspect:

  • `StatusCode`, such as a successful 2xx code or a 4xx/5xx error.
  • `IsSuccessStatusCode`, which indicates whether the response is successful.
  • The response content.
  • Other response metadata when needed.

`EnsureSuccessStatusCode()` is a convenience method that throws when the response does not have a success status code. It is useful when the desired behavior is to turn non-successful HTTP responses into exceptions after obtaining the response.

The talk’s workflow is therefore:

  • Call `GetAsync`.
  • Inspect the response status if custom status handling is needed.
  • Call `EnsureSuccessStatusCode()` when non-success responses should fail the operation.
  • Read and deserialize the response content.
  • Catch `HttpRequestException` around the external operation.

The speaker recommends catching exceptions where the application lacks control, such as external network calls, disk I/O, and other external systems. He warns against wrapping every line of code in `try`/`catch` and against catching the base `Exception` type merely to swallow failures. Catch explicit exception types that the application can handle, and allow programming errors to remain visible.

Response content can be read as a byte array, string, stream, or JSON. The JSON convenience path uses `System.Text.Json`. If its default behavior is insufficient for the application’s JSON options, the caller can read the content as a string and use its own serializer configuration.

Centralizing configuration with named clients

At [31:06], the sample moves the weather API’s base address out of the page and into the HTTP-client registration.

The API configuration is given the name `weatherAPI`. The page then calls `CreateClient` with the same name. The resulting client has the base address configured during application startup.

This makes environment changes easier. A development, test, acceptance, and production deployment can use different API settings without scattering those changes across every page or service that makes a request.

Encapsulating calls with typed clients

At [33:33], the talk demonstrates a typed client. A typed client is an application-specific class whose constructor accepts an `HttpClient`. The class exposes an API-oriented method such as `GetWeatherAsync`, rather than requiring pages to know how to build a URI, send a request, inspect the response, and deserialize the result.

The page then injects the weather client and calls its method. This keeps the page small and moves HTTP-specific behavior into one class. The typed client can also become the place for API-specific logic such as authorization, response processing, and resiliency behavior.

Vermeir says he personally prefers typed clients because they keep calling code concise, while also emphasizing that named clients are a valid alternative.

Delegating handlers as HTTP middleware

At [36:43], the talk introduces delegating handlers. A `DelegatingHandler` behaves like middleware around an HTTP request and response. It can inspect or modify the outgoing request, call the next handler, then inspect or modify the response as it returns.

The chain has a defined order. A request travels from the `HttpClient` through the registered handlers and finally to the built-in HTTP client handler that performs the actual network operation. The response travels back through those handlers in reverse order.

Each handler typically overrides `SendAsync`, performs work before calling the base implementation, awaits the next handler, and performs response-side work after the await. This allows one handler to log both the outgoing request and the returned response.

The talk gives two examples:

  • A logging handler that records the request URI and response activity.
  • An authentication handler that adds an authorization header. The demo uses a dummy value; in a real application, the handler is a place to obtain a bearer token from an identity provider and attach it to outgoing requests.

Handler order matters. If logging is registered before authentication, the outgoing request passes through logging first and authentication second. On the way back, the authenticated response passes through authentication first and logging second.

Handlers can also be useful in tests. Vermeir describes an open-source testing approach that intercepts HTTP requests and returns stub responses instead of requiring every `HttpClient` call to be mocked separately.

The demo initially fails because the handlers were attached to the client but not registered in dependency injection. After registering them, the logging and authentication chain works. This illustrates that both handler registration and handler attachment are required.

The speaker also describes a limitation of the handler model: it is a fixed request/response chain, not a place to change `HttpClient` or `SocketsHttpHandler` settings after a request is already in progress. Those settings have already been selected and used by that point. He characterizes asynchronous delegating-handler behavior as unavailable in the sense being discussed, while the sample itself uses `await` to move through the chain.

Retries, backoff, jitter, and circuit breakers

At [39:56], the talk turns to resiliency. A network can fail at the exact moment a request is sent, and a remote API can also be throttled or temporarily overloaded. The application must decide whether to let the request fail immediately or retry it.

The dangerous approach is synchronized, immediate retrying. Vermeir uses a popular festival’s ticket sale as an example: if an API is down for five minutes while two million clients repeatedly retry, all of those clients may send requests within milliseconds of the service returning. The sudden burst can take the service down again. This is the “thundering herd” problem.

Polly is presented as the library for handling these resiliency policies. The talk uses the `Microsoft.Extensions.Http.Polly` NuGet package for HTTP-client integration. A basic retry policy can be built with `HandleTransientHttpError` and a retry count. The initial demonstration uses three retries:

```text HttpPolicyExtensions .HandleTransientHttpError() .RetryAsync(3) ```

This version retries immediately. The talk then changes it to a wait-and-retry policy so that each attempt is delayed. The sample calculates a delay using two raised to the retry attempt, producing an increasing sequence such as approximately two seconds, four seconds, and so on.

The discussion distinguishes the sample from a suggested default: Vermeir mentions five retries as a good default in conversation, while the demo uses three. The number should not be copied blindly; it affects both user-visible latency and the load placed on the dependency.

Backoff alone may still synchronize many clients if they all use identical delays. Polly’s jitter support adds small variations to the wait time. A nominal two-second delay might become roughly 1.9, 2.2, or 2.3 seconds for different callers. This spreads requests over time and gives a recovering service a better chance to stabilize.

A circuit breaker provides a second layer of protection. In the demo, the breaker allows three consecutive failure events before opening and remains open for five seconds. While open, calls are blocked rather than sent to the failing endpoint.

After the open interval, the circuit enters a half-open state and permits a test call. A successful test closes the circuit and allows normal traffic again. A failed test trips the breaker again. The sample also adds callbacks for the break, reset, and half-open events, allowing state changes to be logged. The circuit breaker is combined with the retry policy so that repeated failures do not produce unlimited traffic against an unavailable service.

Key Takeaways

  • Every `HttpClient` instance has its own connection pool. Creating many instances does not provide a shared pool automatically.
  • Do not create and dispose an `HttpClient` for every request. The talk’s 20,000-request demo eventually runs out of connections and throws a socket exception.
  • Reusing a client avoids repeatedly performing DNS resolution, TCP handshakes, and TLS handshakes.
  • A direct long-lived `HttpClient` is one valid option, but `IHttpClientFactory` is the preferred general-purpose pattern shown in the talk.
  • Factory-created clients can be short-lived because the factory reuses pooled message handlers and connections underneath them.
  • Use named or typed clients to centralize base addresses, authentication-related settings, and other per-API configuration.
  • Be aware of DNS staleness with long-lived connections. A finite connection lifetime can force periodic reconnection and DNS refresh; the talk gives 15–30 minutes as illustrative values.
  • Factory handler pooling can also share cookie containers across client instances, so sensitive cookie usage requires caution.
  • Use `GetAsync` when the caller needs to inspect HTTP status codes. `EnsureSuccessStatusCode()` is a concise way to turn non-success responses into exceptions.
  • Catch targeted exceptions such as `HttpRequestException` around calls to external systems instead of placing broad `catch (Exception)` blocks everywhere.
  • Delegating handlers provide ordered middleware for logging, authorization, testing, and response processing. Requests move down the chain; responses move back in reverse order.
  • Polly retry policies should use increasing delays and jitter to reduce thundering-herd behavior. Circuit breakers stop sending traffic to an endpoint that is repeatedly failing.

Practical Notes

Choose the lifecycle architecture

For a simple application that can safely keep one client for a long time, reuse a single long-lived `HttpClient` rather than creating one per operation. If the application calls several APIs, needs centralized configuration, or already uses dependency injection, register clients through `IHttpClientFactory`.

If the backend’s IP address can change without the application controlling the timing, configure a finite connection lifetime. This trades a bounded period of possible DNS staleness for more frequent connection establishment.

Register the factory in dependency injection

The console demonstration uses the following basic shape:

```csharp var services = new ServiceCollection();

services.AddHttpClient();

var provider = services.BuildServiceProvider(); var factory = provider.GetRequiredService<IHttpClientFactory>();

var client = factory.CreateClient(); var text = await client.GetStringAsync(uri); ```

The demo adds `Microsoft.Extensions.DependencyInjection` and `Microsoft.Extensions.Http`. In an application, inject `IHttpClientFactory` rather than resolving it manually at every call site.

Configure a named client

A named client keeps API-specific settings in the startup or bootstrapping code:

```csharp services.AddHttpClient("weatherAPI", client => { client.BaseAddress = weatherApiBaseAddress; }); ```

The caller can then request the configured client:

```csharp var client = factory.CreateClient("weatherAPI"); ```

The base address variable represents the environment-specific weather API address. The point of the pattern is that callers use the name instead of duplicating the address and other configuration.

Configure a typed client

A typed client accepts `HttpClient` in its constructor and exposes an application-specific method:

```csharp public sealed class WeatherClient { private readonly HttpClient client;

public WeatherClient(HttpClient client) { this.client = client; }

public async Task<WeatherForecast[]> GetWeatherAsync() { var response = await client.GetAsync("weather"); response.EnsureSuccessStatusCode();

return await response.Content.ReadFromJsonAsync<WeatherForecast[]>(); } } ```

Register it with the generic `AddHttpClient` overload:

```csharp services.AddHttpClient<WeatherClient>(client => { client.BaseAddress = weatherApiBaseAddress; }); ```

The page or service then injects `WeatherClient` and calls `GetWeatherAsync`. The talk presents typed clients as a way to keep UI code small and encapsulate API-specific behavior.

Handle status codes and external failures deliberately

Use `GetAsync` when status inspection matters:

```csharp try { var response = await client.GetAsync(uri);

if (!response.IsSuccessStatusCode) { // Inspect or handle the status code here. }

response.EnsureSuccessStatusCode();

var result = await response.Content.ReadFromJsonAsync<WeatherForecast[]>(); } catch (HttpRequestException) { // Handle an external network or HTTP failure. } ```

The JSON convenience reader uses `System.Text.Json`. If the required JSON options are not supported by that convenience path, read the response as a string and apply a separately configured serializer.

Keep exception handling near operations whose failure is outside the application’s control, such as network I/O and disk I/O. Do not use a broad exception catch as a substitute for validation or reliable program design.

Register and order delegating handlers

The demo registers its handlers with dependency injection and attaches them to an HTTP client:

```csharp services.AddScoped<LoggingHandler>(); services.AddScoped<AuthenticationHandler>();

services.AddHttpClient("weatherAPI", client => { client.BaseAddress = weatherApiBaseAddress; }) .AddHttpMessageHandler<LoggingHandler>() .AddHttpMessageHandler<AuthenticationHandler>(); ```

The important implementation details are:

  • The handler types must be registered in dependency injection.
  • The handlers must be attached to the relevant client.
  • Registration order affects request and response order.
  • A logging handler can log before and after `await base.SendAsync(...)`.
  • An authentication handler can add an authorization header before passing the request onward.
  • Client and underlying handler settings cannot be changed after the request has entered the chain.

Add Polly retry policies

Install `Microsoft.Extensions.Http.Polly` for the HTTP integration described in the talk. The initial retry example handles transient HTTP failures and retries three times:

```csharp var retryPolicy = HttpPolicyExtensions .HandleTransientHttpError() .RetryAsync(3); ```

For delays, use a wait-and-retry policy. The talk’s example increases the delay using the retry attempt:

```csharp var retryPolicy = HttpPolicyExtensions .HandleTransientHttpError() .WaitAndRetryAsync( 3, retryAttempt => TimeSpan.FromSeconds(Math.Pow(2, retryAttempt))); ```

Attach the policy through the HTTP client’s policy-handler integration. Add jitter to avoid having many clients retry at exactly the same intervals.

The circuit-breaker configuration demonstrated in the talk allows three failure events, opens for five seconds, and provides callbacks for break, reset, and half-open transitions. Combine the breaker with the retry policy when repeated failures should stop producing requests against the unavailable service.
