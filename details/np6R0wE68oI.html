What This Video Is About

This video provides an in-depth discussion on architectural patterns and strategies for modernizing legacy systems, particularly when applying Domain-Driven Design (DDD) principles. The central theme is that while established patterns exist, real-world legacy migrations involve numerous granular decisions that these high-level patterns do not fully cover. The speaker details fundamental "building blocks" required to manage the transition from an old system to a new one, addressing challenges like data model translation and maintaining consistency between parallel systems.

The discussion also explores how modern practices, specifically Artificial Intelligence (AI), can be integrated into this complex migration process. It is emphasized that while AI can assist in managing large, multi-codebase projects, deterministic tools and human insight remain crucial for ensuring the reliability of the modernization effort. The presentation uses examples from the company Payit to illustrate these concepts in practice.

Detailed Walkthrough

The speaker begins by framing legacy system modernization as a process requiring constant micro-decisions rather than just following established patterns [0:00]. When modernizing, one must decide how to handle operations—whether to move consumers writing to the old system to the new one (write operation migration) or build and migrate read operations from the old API to a new one [1:34].

Key building blocks for modernization include managing domain concepts across systems that may have evolved over time, running the new and old systems in parallel, defining request routing between them, and critically, mapping models—deciding what functionality to keep, evolve, or discard [5:00]. Furthermore, even years into a project, one must continually revisit the legacy system to understand core functionalities that might not have been documented [5:38].

Regarding implementation depth, there are two main approaches: rewriting the entire legacy system in a new language while keeping its structure, or migrating and improving pieces incrementally [12:04]. Modularity is another challenge; legacy systems often have scattered dependencies that do not fit neatly into modern architectures [15:38].

The speaker then discusses synchronization strategies necessary when both old and new systems operate concurrently. The primary methods are Domain Events and Change Data Capture (CDC), though batch import jobs or shared databases can also be used [16:04]. At Payit, the team moved toward an event-driven architecture but found that relying solely on publishing events from legacy code was risky because of numerous undocumented workflows or infrequent processes like monthly batch imports [23:08]. CDC addresses this by using database triggers to publish changes automatically upon modification, though it risks losing business context associated with a data change [26:14].

DDD patterns offer further guidance. The "Bubble" pattern suggests starting with a new domain model and potentially a new data store, synchronizing at the data level (e.g., using CDC or outbox patterns) [30:08]. Another variation involves keeping the legacy system as is but migrating piece by piece while fixing and improving things simultaneously [12:46]. The choice between these approaches hinges on how much of the legacy code one wishes to touch versus building fresh components, which relates directly to the domain model [35:00].

When running systems in parallel, challenges arise, notably asymmetrical validation. For instance, if the new system enforces stricter rules (e.g., disallowing emojis in emails), it may receive data from the legacy system that violates those new rules, forcing short-term compromises [25:48].

The speaker details two primary migration tracks used at Payit's employee management domain. One track focused on migrating the "right model first" (the concept of an Employee/Collaborator), building a new autonomous bubble (System C) to become the source of truth for personal information, and then synchronizing this data out to legacy systems A and B [38:04]. The other track involved prioritizing events first, where the legacy system published events based on its existing model, forcing consuming domains to translate that legacy model into their new domain models [45:12]. Despite the apparent simplicity of event-first migration, it proved complex due to numerous undocumented workarounds and use cases embedded in the legacy system's data structure across different countries [48:00].

Finally, AI was applied to streamline cleanup tasks within a modernization program. The team created a project management tool using a Git repository populated with Markdown files containing front matter YAML for status tracking. This allowed AI agents access to raw project data without needing external APIs [51:32]. To ensure reliability, the speaker stressed building deterministic tools—using OpenAPI specs instead of asking AI to discover endpoints, and forcing AI instructions with specific algorithms (e.g., detailing file traversal from API route to service layer) rather than just stating an end goal [57:04].

Key Takeaways

  • Legacy modernization requires addressing numerous micro-decisions beyond what high-level architectural patterns fully cover.
  • Core building blocks include deciding on write operation migration versus read operation migration, managing domain concept translation, and defining request routing between old and new systems.
  • Synchronization strategies between parallel systems primarily involve Domain Events or Change Data Capture (CDC), though other methods exist.
  • The "Bubble" pattern offers choices regarding where data model mapping occurs: either entirely in code during synchronization or at the data level via scripts/CDC.
  • Running systems in parallel introduces challenges like asymmetrical validation when new systems enforce stricter rules than legacy ones.
  • AI can accelerate migration by managing complex, multi-codebase projects, but its effectiveness relies on building harnesses around it.
  • A key principle for using AI reliably is prioritizing deterministic tools (like reading OpenAPI specs) over asking the AI to discover information autonomously.
  • When instructing AI, providing a highly specific algorithm or end state with required steps yields better results than simply stating an objective.

Practical Notes

  • Migration Approaches: Two main strategies discussed are rewriting the legacy system in a new language while maintaining its structure, versus migrating and improving pieces incrementally [12:46].
  • Data Synchronization Choices: Use Domain Events or CDC to keep data consistent between systems with different databases.
  • Model Mapping Decision Point: Decide whether to start by building a new write model (Right Model First) or by consuming events from the legacy system and translating them into the new domain model (Events First).
  • AI Implementation Detail: To make AI useful, structure project data in Git repositories using Markdown files with YAML front matter for status tracking.
  • Reliability Technique: When analyzing code with AI, force it to follow a specific sequence of steps (e.g., API route -> controller -> service -> data access) and reference line numbers rather than allowing it free optimization [59:04].
